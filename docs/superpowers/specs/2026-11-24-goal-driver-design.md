# 요구사항에서 납품까지: 목표 기반 실행 설계

상태: 구현 전 설계안 · 기준 코드 `b7b3a18` · [작업지시서](../plans/2026-11-24-goal-driver.md)

## 1. 결정과 범위

CineForge가 목표와 다음 행동을 소유한다. Pi는 요청 해석 보조와 외부 작업 수행을 맡을 수 있지만 승인자나 완료 판정자를 대신하지 않는다. 호스트가 CLI 명령 순서를 추론하는 대안은 변경량이 작지만 호스트가 바뀔 때마다 종료·복구 정책도 달라진다. 반대로 새 범용 에이전트를 만드는 안은 기존 파이프라인과 권한 체계를 중복하므로 채택하지 않는다.

첫 버전은 **텍스트 스토리보드**와 **최종 MP4 납품** 두 목표에 한정한다. 단일 컷 수정, 이미지 보드, 게시, 다중 납품은 지원한다고 추정하지 않는다. 모호하거나 지원 밖이면 원문을 보존하고 질문한다. ‘15초’는 검증 조건이지 ‘영상 생성 허가’가 아니다. 기존 프로젝트·수동 명령의 의미는 바꾸지 않는다.

## 2. 목표 계약과 소유권

신규 `goal.json` 예시:

```json
{"version":1,"revision":1,"kind":"text_storyboard","request":"15초 9:16 광고 스토리보드만","constraints":{"duration_s":15,"aspect":"9:16"},"source":"explicit_request"}
```

지원 kind는 `text_storyboard`, `delivery_mp4`. 명시된 납품 형식과 긍정·부정 표현을 먼저 해석한다. ‘영상은 만들지 말고 보드만’은 전자, ‘보드부터 만들고 마지막에는 MP4로’는 후자다. 후보가 하나로 좁혀지지 않거나 검증할 수 없는 필수 조건이면 목표를 활성화하지 않는다. 원문과 후보·미해결 조건을 상태 출력에 남기고 사용자가 범위를 확정한다. 모델 출력은 제안일 뿐이며 임의 명령이나 검사식을 받을 수 없다. 제약을 조용히 삭제하지 않는다.

- `goal.json`: 요청과 완료 조건의 기준. 허용 행동과 검증기는 kind별 코드 목록으로 결정한다. 변경은 명시적 확인 후 revision을 증가시킨다.
- `progress.json`, SSOT, `authority.json`, 실행 계획, 기존 영수증: 각각의 기존 역할 유지. 목표 변경으로 실행 권한을 추가하지 않는다.
- 신규 `goal/attempts/`: 행동을 시작하기 전에 기록하는 시도 식별자·입력 해시·상태·외부 작업 ID. 산출물의 별도 대장이 아니다. 검증 결과에는 판정 시점의 revision·입력 및 출력 해시를 붙인다. 파일이 바뀌면 과거 성공 표시를 재사용하지 않는다.

## 3. 완료 판정표

| 목표 | 필요한 산출물과 검사 | 금지 또는 불충분한 증거 |
|---|---|---|
| 텍스트 보드 | S06에서 만든 scene/camera/motion 자료로 순서 있는 컷 목록 확인. 컷 ID 고유성, 카메라 지시와 컷 연결, 양의 길이, 명시한 화면비와 계획 일치, 목표 총길이와 차이 ≤ 1프레임(계획 fps 기준). 사용자에게 보드 경로 반환 | S06 done만으로 완료 불가. S07 이후 단계 및 이미지·음성·영상 생성 금지 |
| MP4 납품 | 현재 렌더의 규격·길이와 요청 비교, 기술 QA, 기존 gate, 필요한 playback 검수, 현재 렌더에 대한 G3 사용자 승인, `final/delivery.json`과 실제 `final/<project>.mp4` 해시 일치. 원본 렌더와 납품본도 동일해야 함 | 파일 존재나 `deliver` 반환만으로 완료 불가. 자동 시청 확인, 자동 승인, 게시 금지 |

G3는 현재 `Project._g3`의 승인 기록 존재 검사만으로는 부족하다. 목표 모드의 승인 명령은 사용자 확인 시 렌더 SHA-256을 함께 기록한다. 기존 승인에 해시가 없으면 목표 모드에서만 재확인한다. 복구 시에도 `delivery.deliver()`를 조회 용도로 부르지 않는다(파일을 작성하는 함수다).

## 4. 실행과 중단

`new ... --goal auto|text_storyboard|delivery_mp4`로 선택 도입한다. `auto`가 모호하면 프로젝트만 만들고 질문한다. `goal show PROJECT --json`은 읽기 전용, `goal set PROJECT --kind KIND`는 명시적 확정, `goal drive PROJECT`는 진행 또는 재개다. 기존 `run --until`은 운영자용 중단점이지 목표 달성 증거가 아니다. 목표 프로젝트에서는 `run`도 목표의 단계 상한을 넘길 수 없다. 수동 외부 실행 명령 역시 목표의 금지 작업을 거부한다. 목표 없는 기존 프로젝트는 그대로 실행한다.

반복 순서: 프로젝트 실행 잠금 → 목표·현재 해시 읽기 → 완료 검사 → 부족한 조건 하나 선택 → 허용 행동·기존 권한 확인 → 한 행동 실행 → 증거 재평가. 기존 `Project.run(until=...)`은 이미 완료된 단계를 건너뛰므로 단순히 반복 호출하지 않는다. **단일 단계** 실행을 추출해 허용 여부를 실행 직전에 검사한다. 로컬 편집·렌더는 기존 함수에 위임한다. 외부 작업은 한 번만 인계하고 결과가 도착한 뒤 같은 drive로 재개한다. 데몬이나 Pi 자동 기동은 첫 버전 범위 밖이다.

| 판정 | 반환 상태 | 진행을 다시 시작하는 조건 |
|---|---|---|
| 모든 조건 충족 | `satisfied` | 새 목표 또는 증거 변경 |
| 목표 모호 / 승인 없음 / 사용자 검수 필요 | `needs_user` | 범위 확정 또는 대상 해시에 대한 승인 |
| 외부 실행에 유효한 요청을 발행 | `waiting_external` | 동일 요청 ID 및 입력 해시에 대응하는 결과 수신 |
| 원격 접수 여부 불명 | `needs_reconciliation` | 기존 작업 조회·수동 대조. 자동 재전송 금지 |
| 수정 불가 / 반복 / 지원 안 되는 실행 환경 | `blocked` | 사유와 부족한 증거를 표시. 사용자 수정 뒤 재평가 |

`drive --json` 출력 계약: `state, goal_revision, unmet, next_action, evidence, reason`. 종료 코드 0=충족, 2=입력 오류, 3=사용자/외부 대기, 4=차단/대조 필요. 단계 내부의 done은 이 상태를 대신하지 않는다. 작업 키는 프로젝트·revision·행동·입력 해시로 만들고 키별 의도 기록을 원자적으로 저장한 뒤 부작용을 시작한다. 동시 drive는 하나만 실행하고 다른 쪽은 busy(3)로 종료한다. 잠금은 프로세스 종료 시 풀리는 OS 잠금 사용. 오래된 응답은 이력으로만 남긴다. 목표 revision이 바뀌어도 이전 원격 작업 대조 전 동일 작업을 새로 보내지 않는다.

## 5. 수정 및 검증 경계

자동 수정 1호는 보드의 총길이만 어긋난 경우다. 컷별 고정 시간 지정이 없고 목표 프레임 수가 컷 수 이상이면 기존 길이 비례로 양의 정수 프레임을 배분하고 잔여 프레임은 소수 잔여 큰 순(동률은 컷 순서)으로 배분한다. 기존 잠금이나 보존 조건이 있으면 수정하지 않는다. 기존 SSOT 변경 영향 경로를 적용하고 재검사한다. 다른 창작 품질 문제는 합격을 추정하지 않는다. 동일 행동·입력·실패가 재발하면 즉시 차단, 한 drive당 최대 32행동에서 중단한다. 유료 호출에는 이 수정 예산을 적용하지 않는다.

출시 조건: 두 목표에 대해 처음 요청부터 완료/정당한 대기까지 CLI 테스트, 공급자 호출 횟수 검사, 프로세스 중단·동시 실행·렌더 교체·구형 프로젝트 회귀를 통과해야 한다. 실 공급자 호출이나 결제 없이 검증한다. 구체적 수행 순서는 연결된 작업지시서를 따른다.
