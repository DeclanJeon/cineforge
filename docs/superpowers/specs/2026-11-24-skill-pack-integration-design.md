# CineForge 스킬팩 독립 배포 설계

상태: 승인 설계 · 별도 워크트리 구현

대상: `cineforge`와 `contents-production-skills`

## 1. 목표와 현재 문제

**동일한 CineForge 바이너리에서 호환되는 스킬팩만 교체하면, 새 프로젝트의 담당 스킬·참조 문서·제작 지침이 새 팩을 따라야 한다.** 프로젝트를 만드는 명령은 그대로이며, 팩을 바꾼다고 승인·비용·납품 조건이 바뀌지 않는다. 이미 진행 중인 프로젝트는 팩이 바뀌어도 기존 제작 근거를 유지한다.

현재는 팩을 탐색하지만 역할 분리가 배포 단위까지 이어지지 않는다.

| 현재 위치 | 결합 지점 | 목표 |
|---|---|---|
| `cineforge/data/pipeline.yaml` | 단계·권한·출력뿐 아니라 담당 스킬·라우트도 번들에 포함 | 단계·권한·출력은 엔진에 유지, 담당·라우트는 팩에서 조회 |
| `cineforge/pipeline.py`의 `_handoff()` 및 단계별 보강 문구 | 모션·컷 수정 등의 참조 경로와 읽을 순서를 Python 코드에 기재 | 엔진은 프로젝트의 사실만 전달, 해당 사실에 연결된 참조·지침은 팩에서 조회 |
| `cineforge/skills.py`, `cineforge/delivery.py` | 엔진에 필수 파일 목록을 고정하고, 납품 시 그때 설치된 파일을 다시 해시 | 팩이 파일을 선언하고 프로젝트에 고정된 버전과 실제 작업 기록을 구분해 보고 |
| `cineforge/progress.py`, `cineforge/ui.py`, `cineforge/cli.py` | 진행 화면과 JSON이 번들 YAML의 담당 스킬을 표시 | 화면과 인계가 같은 프로젝트 바인딩에서 담당을 읽음 |
| 스킬팩 `manifest.json`과 `creative-production/references/{skill-map.md,craft-bridge.csv}` | 팩 자체에도 설치 목록과 제작 라우팅이 따로 존재 | 기존 매니페스트를 확장하고, CineForge 인계용 매핑은 팩 안에서만 관리 |

참고: 현재 소스에는 작업 중인 코드 모션 변경도 있다. 이 변경들은 본 설계의 전제나 이미 배포된 동작으로 간주하지 않는다.

## 2. 비교한 방식과 결정

1. **기존 경로를 인터페이스로 취급:** 지침 수정은 독립 배포 가능하지만, 파일 이동이나 담당 교체 때 CLI를 고쳐야 한다. 채택하지 않는다.
2. **버전이 있는 선언형 팩 인터페이스:** 엔진에는 고정 단계 ID와 제한된 사실만 남기고 팩이 담당·라우트·자료를 선언한다. **채택한다.** 스킬 변경이 한 저장소에 모이고, 같은 CLI에 팩 A/B를 장착하는 테스트로 독립성을 증명할 수 있다.
3. **팩에 상태 기계와 실행 플러그인도 위임:** 자유도는 높지만 팩 변경만으로 승인·검수 조건을 바꾸거나 설치만으로 코드를 실행할 수 있다. 범위에서 제외한다.

### 소유권

- **CineForge:** 프로젝트 ID와 상태 전이, 단계 ID·순서·작업률, 입출력 스키마와 SSOT, 승인·비용·실행 봉투, 증거·영수증 검증 및 납품 게이트. 요청이 제작 대상인지 판정하는 `cineforge route`, 엔진의 콘셉트 데이터와 규칙, 현재 엔진이 수행하는 공급자 호출 및 실행 검증도 이동하지 않는다. 팩이 정하는 `route`는 프로젝트 내부 단계에 붙는 제작 라우트다.
- **스킬팩:** 기존 단계의 담당 스킬·라우트, 조건별 참조·제작 지침, 스킬 내부 프롬프트·레시피·스크립트, 팩 파일 인벤토리. 특정 제작 레시피를 가이드할 수 있지만 실행 승인·공급자 권한·검수 통과를 선언할 수 없다.
- **호스트 에이전트:** 패킷이 지정한 팩의 스킬·자료를 읽고, 기존 승인 범위 안에서 작업하고 증거를 반환한다. 기본 경로에서 우연히 찾은 동명의 스킬로 대체하지 않는다.

## 3. 팩 계약 v1

기존 팩의 `manifest.json`에 `integrations.cineforge`를 추가한다. 릴리스 시 같은 매니페스트에 팩 버전, 인계 매핑, 파일 인벤토리가 함께 나간다. 기존 설치 목록 `skills`를 그대로 사용한다. 아래는 발췌이며 실제 팩에는 엔진이 요구하는 모든 단계가 있어야 한다.

```json
{
  "integrations": {
    "cineforge": {
      "contract_version": 1,
      "stages": {
        "S06_storyboard": {
          "route": "R10",
          "owners": ["storyboarding-video", "camera-spatial-design"],
          "refs": [],
          "guide": "storyboarding-video/references/narrative-panels.md",
          "when": {
            "cut_revision": {
              "refs": ["video-production-assets/references/21-generated-video-qa-retry.md"]
            }
          }
        }
      },
      "delivery_files": ["recording-production-history/scripts/production_history.py"],
      "inventory": "integrations/cineforge/files.json"
    }
  }
}
```

- `name`, `version`, `skills`는 기존 최상위 필드다. `contract_version`은 CineForge가 읽는 계약 버전이며 팩 버전과 별개다. v1 호환 여부는 계약 버전으로 판정한다. 미지원 버전은 거부하며 묵시 다운그레이드하지 않는다.
- `stages`의 키는 엔진의 정식 단계 ID다. 팩이 단계나 산출물을 추가·삭제하거나 권한 정책을 덮어쓸 수 없다. `owners`는 읽을 순서대로 팩의 `skills` ID를 가리키며, 각 ID는 팩의 `SKILL.md` 파일에 대응한다. `route`는 문자열 또는 `null`인 팩 내부 식별자로, 권한 판단에 사용하지 않는다. `refs`는 팩 상대 경로 배열이고 `guide`는 선택적 문서 경로다. 제목 앵커는 별도 필드로 넣지 않고 문서 안의 링크로 안내한다.
- `when`은 엔진이 제공하는 제한된 불리언 사실 이름만 키로 쓴다. v1은 `cut_revision`, `code_motion`, `realtime_3d`만 지원한다. CLI는 컷 수정 플래그, 검증된 기획안 필드 및 기존 요청 분류 결과에서 사실을 얻고, 팩은 어느 단계에서 어떤 파일을 덧붙일지만 정한다. 기본 참조 먼저, 일치 조건은 위 순서대로 병합하며 중복 경로는 첫 항목을 유지한다. 지원되지 않은 사실은 별도 엔진 배포의 대상이다. 새로 생긴 제작 기법의 키워드를 엔진에 추가하지 않으려면 기존 단계 가이드 안에서 호스트가 고르게 한다. 임의 표현식·정규식·셸 명령·동적 모듈을 팩 계약으로 해석하지 않는다.
- 인벤토리는 팩 상대 경로 → SHA-256 매핑이다. 배포 시 팩 저장소가 작성하고, 팩 소유 스킬 트리의 지침·참조·스크립트·보조 모듈·템플릿을 포함한다. 매니페스트와 인벤토리 자체는 별도로 해시한다. 설치기가 덧붙이는 파생 `support/` 복사본은 중복 등록하지 않는다. 담당 진입점, 가이드, 참조 및 `delivery_files` 항목은 전부 인벤토리 안에 있어야 한다. `delivery_files`는 납품에 표시할 관리 대상 목록이지 실행 이력이 아니다.
- CineForge가 소유하는 스키마로 이 섹션을 검사하고, 팩 릴리스 테스트가 배포 전에 같은 계약을 검사한다. CineForge 확장 섹션의 미지 필드·중복 ID·불완전 단계·누락 파일·해시 불일치는 차단한다. 팩의 다른 매니페스트 필드는 기존 설치기와 다른 소비자가 계속 소유한다. 경로는 팩 루트 기준의 상대 파일로 제한한다. 절대 경로·상위 경로·루트 밖으로 해석되는 링크는 거부하고, 사용자가 명시적으로 장착한 로컬 팩의 관리 영역만 읽는다. 검증은 호환성과 로컬 무결성 검사이지 팩의 게시자 인증이나 실행 승인이 아니다.

## 4. 장착 → 고정 → 인계

1. **탐색:** `cineforge skills --root <경로>`는 지정한 팩만 진단한다. 실제 프로젝트는 `CINEFORGE_SKILL_PACK`을 최우선으로 읽는다. 미지정이면 현재 지원하는 호스트 스킬 루트에서 설치본을 찾는다. 소스/독립 설치본의 루트 `manifest.json`과 기존 복사 설치기의 `video-production-assets/support/manifest.json` 위치를 지원한다. 지원 폴더에 있는 매니페스트라도 스킬 파일 경로는 *상위 스킬 설치 루트*를 기준으로 해석한다. 예외는 `inventory` 경로로, 매니페스트가 있는 디렉터리 기준이다. 복사 설치기는 해당 인벤토리를 지원 매니페스트와 함께 복사하고, 인벤토리 내 경로는 스킬 설치 루트 기준으로 검사한다. v1은 `integrations/cineforge/files.json`으로 고정해 설치기가 제공 파일 외의 임의 경로를 복사하지 않게 한다. 로컬 심볼릭 링크 설치처럼 스킬 디렉터리만 연결되어 있으면 `CINEFORGE_SKILL_PACK`을 실제 팩 저장소 루트로 지정한다. 동일 실체는 중복 제거하고 서로 다른 팩이 여럿이면 명시 경로를 안내한다. 설정 오류를 다른 설치본으로 숨기지 않는다.
2. **검증 및 바인딩:** 새 일반 프로젝트는 폴더 생성 전에 팩과 계약을 검사하고 `skill_pack.lock.json`을 저장한다. 고정 정보는 팩 이름·버전·계약 버전·매니페스트 및 인벤토리 해시·정규화한 단계 매핑·파일 해시다. 장착 위치는 탐색 힌트이고 동일성에는 포함하지 않는다. 경로를 옮겨도 동일 바이트의 팩으로 재개할 수 있다. 네트워크에서 최신 팩이나 의존성을 받아오지 않는다. 팩 없는 `analyze`와 명시적 `--provider mock` 오프라인 구조 테스트는 가능하되, 미바인딩 mock을 실제 외부 인계·실행·납품 경로로 승격시키지 않는다.
3. **인계:** `handoffs/<stage>.json`의 기존 `owner_skills`, `route`, `craft_refs`는 바인딩된 팩에서 채운다. 팩 신원·해시, 검증된 루트, 실제 오너 진입점과 가이드 경로를 추가한다. 호스트가 이 경로로 읽도록 하고, `status`·진행 공유 JSON도 동일 매핑을 보여준다. core의 `inputs`, `outputs_expected`, 권한, 증거 규칙은 팩 데이터와 별도 슬롯에서 생성한다. 팩의 도구·가이드 파일은 인계에 노출될 뿐 자동 로드·실행되지 않는다.
4. **재개:** `status`와 과거 납품 조회는 잠금 기록만으로 가능하다. 인계 발행·외부 실행 준비·완료 기록·신규 납품처럼 새 근거가 생기는 지점에서는 동일 팩인지 재검사한다. 파일을 바꿔치기했거나 판독할 수 없으면 중단하고 요구 팩 버전·해시와 복구 방법을 출력한다. 사용자가 버전별 장착 폴더를 유지하거나 이전 릴리스를 별도 경로에 복원해 재개한다. v1에서는 기존 프로젝트에 다른 팩을 자동 병합하거나 잠금을 다시 찍지 않는다. 팩 변경이 필요하면 새 프로젝트를 열며 승인·영수증을 복사하지 않는다.
5. **이력:** 인계에 팩 신원을 남기고 검증된 완료 근거와 연결한다. 납품 문서는 프로젝트에 고정된 팩의 버전·해시와 실제 사용이 증거로 확인된 항목을 분리한다. 팩에 포함되었다는 이유만으로 도구 실행을 주장하지 않으며 근거가 없으면 미확인으로 기록한다. 납품 순간의 전역 설치본으로 잠금이나 과거 근거를 덮어쓰지 않는다.

`cineforge skills` 진단은 팩 위치·버전·계약 버전과 `ready / missing / incompatible / invalid / ambiguous` 상태를 보여준다. 장착·진단 자체에는 외부 호출이나 프로젝트 변경이 없다. 다른 스킬이 사용하는 작업용 데이터나 자격 증명을 인벤토리로 가져오지 않는다.

## 5. 전환과 배포

1. **팩 먼저:** 팩 릴리스에 v1 선언·인벤토리와 검증을 추가한다. 기존 `manifest.json`의 설치 목록·지원 매니페스트 복사 구조를 유지한다. 에이전트용 문서에서 CineForge 인계는 패킷을 우선하도록 정리한다. `craft-bridge.csv`의 자유 서술 조건은 호스트용으로 남기고 CLI에 동일 의사결정표를 다시 쓰지 않는다.
2. **엔진 한 번:** 팩 리더와 프로젝트 바인딩을 붙이고, 인계·진행·납품의 조회를 해당 인터페이스로 통일한다. 새 모드의 `pipeline.yaml`에서 담당·라우트 중복을 제거한다. 엔진 카탈로그의 문서용 담당 스킬은 실행 조회에 사용하지 않는다. 권한·입출력 계약과 독립적으로 변경하며 원래의 외부 승인 경로를 회귀 테스트한다.
3. **기존 프로젝트 보호:** 잠금이 없는 기존 프로젝트는 `legacy/unpinned`로 표시하며 읽기와 기존 인계를 유지한다. 전환 릴리스에서는 기존 프로젝트에만 기존 동작을 남기되, 새 팩이 과거 작업에 쓰였다고 소급 기록하지 않는다. 신규 프로젝트는 매니페스트 없는 팩으로 묵시 폴백하지 않는다. 레거시 제거와 프로젝트 내 업그레이드는 별도 결정이다.
4. **이후 독립 배포:** 가이드·프롬프트·파일 경로·담당 스킬·단계별 참조·팩 안의 스크립트 구현을 바꾸면 팩을 재배포한다. 신규 단계 ID, 새로운 CLI 조건 사실, 승인·증거·산출물 계약이나 매니페스트 호환성 변경이 필요할 때만 엔진 릴리스를 검토한다. 이미 확인된 팩 버전과 해시를 새 내용에 재사용하지 않는다. CLI 오류 수정은 물론 팩 배포와 무관하게 가능하다.

## 6. 인수 기준

| 검증 | 합격 기준 |
|---|---|
| **독립 배포** | CLI wheel 하나를 설치한 뒤 호환 팩 A와 B를 번갈아 장착한다. A/B에서 같은 요청의 같은 단계 ID를 실행하면 새 프로젝트의 담당·참조·화면이 각각 팩을 따르되, 단계 순서·예상 출력·권한 요구는 동일하다. 새 CLI 빌드가 없어야 한다. |
| **진행 프로젝트 재현** | A에 바인딩된 프로젝트에서 전역 설치를 B로 바꾸면 조회는 가능하되 A가 없는 상태에서 신규 인계·완료를 차단한다. 동일한 A를 다른 경로에 복원하면 재개하고, 납품 근거에 B가 찍히지 않는다. 같은 버전 번호로 파일만 바꾼 경우도 차단한다. |
| **팩 검증 및 장착** | 소스 루트와 실제 설치기로 만든 지원 매니페스트 배치 모두를 검사한다. 미지원 계약, 필수 단계·파일 누락, 잘못된 해시, 루트 밖 경로, 모호한 복수 설치가 각각 진단된다. 명시 장착 오류에서 조용한 폴백이 없어야 한다. |
| **권한 불변** | 팩이 `authority`·`outputs_expected` 등을 주입하면 계약 검증이 거부한다. 유효 팩을 바꿔도 무승인 외부 실행은 차단되며 검증되지 않은 산출물을 완료·납품할 수 없다. 진단 중 팩 코드 실행·네트워크 요청은 없어야 한다. |
| **기존 흐름 보호** | 과거 프로젝트와 `analyze`, 오프라인 mock 회귀 테스트를 통과한다. mock 미바인딩이 실제 실행 권한으로 이어지지 않고, 기존 프로젝트 이력에는 미확인 팩 사용을 단정하지 않는다. |

구현, 팩 수정·설치, 실제 릴리스 간 A/B 검증은 이 설계 승인 이후 작업이다.
